# The iOS and Android app

The app is the React interface in `ui/` in a native shell ([Capacitor](https://capacitorjs.com)). It adds what a browser cannot do well on a phone: a first-launch choice of server, sign-in with the platform's secure storage (for a hosted account, also Continue with Google, and Continue with Apple on iOS), an entry in the share sheet and, for a hosted account, the App Store and Google Play purchase sheet for the one-time unlock. Everything you see after signing in is the interface in `ui/`, the same build the server serves to a browser, running against your own server or the hosted service. (The older buildless interface in `web/` is no longer loaded by the app.)

**Status.** Development software, first version. Section [What was and was not verified](#what-was-and-was-not-verified) lists exactly what was run. The purchase code has not met a real App Store or Google Play sandbox; [the purchase section](#the-one-time-purchase) says what that leaves open. Continue with Google and Apple has not met a real Supabase project, Google account or Apple account either; [that section](#continue-with-google-and-apple) says what was run. Resetting a forgotten password has run only in tests and against the stand-in, never on a simulator, a phone or the real project ([A forgotten password](#a-forgotten-password)). No store listing, push notification or on-device page reading exists yet; [what is not done](#what-is-not-done) says where each one attaches.

## What it does

1. **Choose a server on first launch.** *Little Archive account* (the hosted service) or *My own server* (you type its address). The app asks the server what it is (`GET /api/discovery`, which needs no credentials) before sending anything secret, and explains in words what went wrong if it cannot connect. The own-server screen carries short guidance; see [Connecting to your own server](#connecting-to-your-own-server).
2. **Sign in.**
   - *Own server:* the owner password goes once to `POST /api/auth/devices` and is exchanged for a revocable `lad_…` device token. The password is never stored.
   - *Hosted account:* **Continue with Apple** (iOS) and **Continue with Google** (iOS and Android), and under them email and password, all against Supabase Auth's REST routes (sign-up, sign-in, the Apple and Google grants, refresh, sign-out), with the token refreshed before it expires. See [Continue with Google and Apple](#continue-with-google-and-apple). A forgotten password is reset through an emailed link that opens the app ([A forgotten password](#a-forgotten-password)).
   - The credential is kept in the iOS Keychain or an Android Keystore-backed store, never in `localStorage`.
3. **Use the full interface** against that server (browse, search, save, organize, import, export, settings).
4. **Save from the share sheet.** Android: *Little Archive* appears for text and links. iOS: a Share Extension. Both open the app on the ordinary save dialog with the link filled in. Nothing is saved until you tap Save, the same as the `/share` page of the web app ([phone guide](phone.md)).
5. **Account screen** (Settings, "This device"): sign out, switch server and, for a hosted account, delete the account. The dialog says what the server did: the library and the sign-in are both gone (`auth_user_deleted: true`); the library is gone and the sign-in will follow (`auth_deletion: "pending"`, with the server's own sentence); or the library is gone but this service is not set up to remove sign-ins, so the email is still registered (`auth_deletion: "not_configured"`). The words are in `ui/src/features/dialogs/words.ts`.
6. **Unlock** (hosted accounts only): the store's purchase sheet for the one-time unlock, and Restore. See [the one-time purchase](#the-one-time-purchase).

## How it is built

```
ui/                       the React interface (Vite, React, TypeScript): the one interface for the browser, the demo and the app
ui/src/data/backend.ts    the three backends the interface can run on, and NativeBridge and PurchaseBridge, the two halves of the agreement with this app
web/transport.js          the transport: server address + bearer token + native HTTP
mobile/
  app.config.json         the hosted service's address and public Supabase values (the only place they are written)
  src/                    the app shell: boot, onboarding, bridge, purchases, server-url, discovery, setup, supabase, social, recovery, credentials, store, share, files, ui, native.css
  scripts/build-web.mjs   builds ../ui and bundles it, with the shell, into mobile/www
  tests/                  node tests for the shell, the bridge, the purchase logic and the bundle
  dev/stub_supabase.py    a local stand-in for Supabase Auth, for trying the hosted flow on this computer
  ios/, android/          the Capacitor projects (committed as Capacitor intends; Pods, build output and web assets are ignored)
  ios/App/App/StorePurchasesPlugin.swift
  android/app/src/main/java/app/littlearchive/mobile/StorePurchasesPlugin.java
                          the two store plugins (see the purchase section)
  ios/App/App/SocialSignInPlugin.swift
  android/app/src/main/java/app/littlearchive/mobile/SocialSignInPlugin.java
                          the two sign-in plugins (see Continue with Google and Apple)
```

`mobile/www` is generated, never committed. `npm run build:web` runs `vite build --manifest` in `ui/` (which needs `npm ci` there first), then copies into `mobile/www` only what the page `ui/dist/index.html` reaches, found through Vite's manifest, so the public demo that the same project also builds, its records and its photos, stay out of the app (the interface's entry can reach its demo and browser backends; the build leaves those two out, and a test checks that nothing in the bundle refers to a file that is missing). It writes a copy of `index.html` with two changes: a content security policy and the shell's script, `native/boot.js`, in place of the interface's chunk scripts. Then it bundles the shell with esbuild. `mobile/tests/build.test.mjs` tests this against a small fixture shaped like Vite's output, so the mobile-only CI job needs no interface dependencies, and, when `ui/node_modules` exists, against the real build.

**The page is loaded by the shell.** The app's `index.html` starts `native/boot.js`. It finds out which server this phone belongs to, signs in, builds the transport, sets `globalThis.__littleArchiveNative` (built in `src/bridge.js`), and only then imports the interface's entry, a hashed file that the build writes into the shell. The entry's `createBackend()` finds the global and runs the interface on the native backend (`ui/src/data/backends/native.ts`). In a browser the global does not exist and the interface takes the browser backend.

**The two ends of the bridge agree by test.** `NativeBridge` and `PurchaseBridge` are declared in `ui/src/data/backend.ts`. `mobile/tests/bridge.test.mjs` reads that file and checks that the object the shell builds has every required member, nothing the interface does not know, and the same purchase members, for a hosted and for a self-hosted account.

What the interface does differently on the native backend:

| Where | In the app |
| --- | --- |
| every `/api` call and download | `native.fetch` instead of the page's `fetch`: bearer token, native HTTP, only `/api/…`; the interface never sees the token |
| thumbnails | `native.localAsset` recognises a stored thumbnail, and `native.attachImage` fetches it with the token and shows it from a blob URL when the card scrolls near the screen (an `<img>` cannot send a header) |
| sign-in | there is none in the interface: `native.signedOut` hands over to the shell, which clears the credential and reloads to its own sign-in screens |
| Settings | the "This device" section (email, sign out, switch server, delete account) comes from `native.account`; the server address shown is the server's, not the page's |
| exports and backups | `native.saveFile` writes the file to the app's cache and hands it to the share sheet, then it is deleted at the next start |
| a link shared while the app is open | `native.onShare` opens the same save dialog |
| the unlock | `native.purchases` (hosted accounts only) |

**Styling.** The interface's own stylesheet is loaded first, then `src/native.css`, which uses its design tokens (`--paper`, `--ink`, `--sage`, … in both themes) for the screens that run before the interface (choosing a server, signing in) so nothing changes style at sign-in, and supplies the safe-area values the interface reads. It also gives the interface's top bar room for the notch: the bar is `h-16` with `padding-top: var(--safe-top)`, which leaves about 5px for its content on a phone with a dynamic island. The right fix is one line in `ui/src/features/shell/shell.tsx` (`h-[calc(4rem+var(--safe-top))]`); `native.css` compensates until then.

**The keyboard (iOS).** The window's root is `RootViewController` (in `MainViewController.swift`), which holds the web view's controller and pins the web view's bottom edge to the top of the keyboard. It keeps the keyboard's last frame from `keyboardWillChangeFrame` and works the covered height out again on every layout, so a change of size with no word from the keyboard (Split View, Stage Manager) leaves no stale gap; the sum is one pure function, `keyboardCover(keyboard:in:)` (a floating or split iPad keyboard takes no room). Left to itself, a full-screen `WKWebView` keeps its size when the keyboard shows and pans its visible area up to reveal the field: the layout viewport stays put and the visual viewport moves inside it, so `position: fixed` follows the wrong one and the page passes behind the status bar. With the web view ending at the keyboard the two viewports are the same, the page is simply shorter and the document scrolls, so fixed elements hold: the strip of paper that `native.css` keeps under the status bar on the sign-in screens (`.native-screen::before`), and the interface's own strip in `shell.tsx`. The colour behind the (translucent) keyboard is the page's paper, read from the page's theme when the keyboard shows, since the theme can differ from the phone's. Three things follow from the page changing size. `ui.js` brings a focused field that the change left out of view back to the middle of the screen on `resize` (the web view reveals a field when it takes focus, not after a turn of the phone). The controller sets `data-keyboard` on the page's root element while a keyboard taller than 120pt takes room, and the interface hides its dock for as long (`useKeyboardUp` in `shell.tsx`, the same `inert` it uses during a selection), because a dock fixed to the bottom edge would otherwise sit just above the keyboard; the 68pt bar of a hardware keyboard shortens the web view but is not a keyboard, so the dock stays. The selection bar (`library-screen.tsx`) is left to ride above the keyboard: it holds the only actions for a selection, including leaving it. And the bottom sheet (`modal.tsx`) is never taller than the room under the status bar. The web view is also taken off the four keyboard notifications it listens to (will show, will hide, will and did change frame): it gives its scroll view room for the keyboard when the notification arrives, while still full height, and WebKit's source does not work that out again when the frame changes (`WKWebViewIOS.mm`: `_keyboardChangedWithInfo` adjusts, `_frameOrBoundsMayHaveChanged` does not). On iOS 26.5 the room was gone after the frame change even with the web view listening; an older system could not be run, so rather than depend on that the web view is simply not told, which is what Capacitor's own keyboard plugin does for its resize (`@capacitor/keyboard` 8.0.6, `Keyboard.m`, `load`). That plugin is not used: it resizes by setting the root view's frame and hides the accessory bar unless told not to. There is no Swift test target in the project, so `keyboardCover` has no unit test. On Android nothing was needed: Capacitor's `SystemBars` already pads the web view by the keyboard's height.

## Why native HTTP, and no server change

The brief allowed either a tightly scoped CORS allowance on the server or native HTTP. The app uses **Capacitor's native HTTP client, called explicitly** (Capacitor's option to patch `fetch` is off), and the server is **unchanged**.

- A native request is not a cross-origin browser request. There is nothing to allow, so there is no CORS list to keep right, and `capacitor://localhost` and `https://localhost` never become trusted origins. `https://localhost` in particular is the origin of any app that serves from it on Android, and of a stray process on a developer's machine.
- The owner-password routes check `Origin` (`same_origin` in `server/app.py`) and answer 403 to a browser request from another origin. A CORS design would have had to loosen that check for `POST /api/auth/devices`, the most sensitive route. Native requests carry no `Origin` header, so it stays exactly as strict.
- It keeps the hosted guarantee that a cookie is never a credential, and keeps the self-hosted rule that a presented bearer token is judged by itself alone. The app never sends or accepts a cookie (see the cookie note below).
- The web view's own content security policy is `connect-src 'self'`: page script cannot reach any server directly. Only the shell's explicit calls to the native client can, and `web/transport.js` refuses any path that is not an absolute `/api/…` path, so a hostile value in server data (a thumbnail URL on another host, say) cannot carry the token elsewhere.
- Thumbnails need the same fetch-and-blob step under either design (`<img>` cannot send `Authorization`, and a token in a query string would end up in logs), so CORS would not have saved that work.

Costs of this choice: uploads and downloads cross the app's bridge as base64 (an import of 16 MiB is about 21 MiB of text; fine on a phone, and `@capacitor/file-transfer` is the seam if it ever is not), and the web view cannot be pointed at a server's own page.

## Building and running

Needs Node 22 or newer for the Capacitor tools (`mobile/package.json` says so). Use the same Node you run `npm` with.

```sh
(cd ui && npm ci)        # the interface's dependencies, needed to build the bundle
cd mobile
npm ci
npm test                 # shell, bridge, purchase, transport and bundle tests
npm run sync             # build ../ui, make mobile/www, and copy it into ios/ and android/
```

**iOS.** Xcode 26 or newer. The project uses Swift Package Manager (Capacitor 8's default), so CocoaPods is not used.

```sh
open ios/App/App.xcodeproj           # or:
xcodebuild -project ios/App/App.xcodeproj -scheme App -configuration Debug \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro Max' build
```

Run it from Xcode, or install the built `App.app` with `xcrun simctl install booted …` and `xcrun simctl launch booted app.littlearchive.mobile`. A simulator reaches a server on the same Mac at `http://localhost:PORT`. A launch from the command line has no store: the unlock screen offers its buttons but the App Store has no product, and a tap says so. To try a purchase in the simulator, run from Xcode (see [trying a purchase](#trying-a-purchase-without-real-money)).

**Android.** JDK 21 (Capacitor 8 needs it) and the Android SDK.

```sh
cd android
JAVA_HOME=/path/to/jdk21 ANDROID_HOME=~/Library/Android/sdk ./gradlew assembleDebug
# app/build/outputs/apk/debug/app-debug.apk
```

In an emulator, run `adb reverse tcp:PORT tcp:PORT` and use `http://localhost:PORT`. (`http://10.0.2.2:PORT` also reaches the computer, but only a development bundle accepts that address: build the web bundle with `LA_DEBUG_BUILD=1 npm run sync`. The server then sees the host `10.0.2.2` and refuses it unless `LA_PUBLIC_URL` is set to that address; the app shows that explanation. Never ship a bundle built that way. A release bundle refuses the address as "not encrypted", like any other address on a network.) The Android debug build type allows plain http to `localhost`, `127.0.0.1` and `10.0.2.2`, nothing else; release builds allow no cleartext traffic to any host.

## The hosted service's address and keys

`mobile/app.config.json` is the one place they are written:

```json
{
  "hostedServerUrl": "https://app.little-archive.example",
  "supabaseUrl": "https://kzrupzzoaxynlzlzxjwp.supabase.co",
  "supabasePublishableKey": "sb_publishable_…"
}
```

- **`hostedServerUrl` is a placeholder** (`.example` never resolves). Choosing *Little Archive account* says so ("Could not reach app.little-archive.example") until it is replaced.
- The publishable key and Supabase URL are public by design. **No other key or secret may be in the repository or the bundle.** `validateConfig` refuses unknown settings and anything shaped like a secret key, JWT or private key; `build-web.mjs` scans every file it writes for the same and for any `sb_…` key that is not the configured one; `mobile/tests/build.test.mjs` runs both.
- **The sign-in service is pinned.** The app sends an email and password, an Apple identity token, or a Google sign-in's code and verifier only to `supabaseUrl` from this file, opens Google's sign-in only through `<supabaseUrl>/auth/v1/authorize`, and does all of it only after `GET /api/discovery` shows that the server names the same Supabase URL. A server that names another one (a compromised or malicious server, or someone's own hosted deployment) is refused: "this app does not trust it, so it will not send your email or password there." Typing a hosted server's address under *My own server* works only when it passes this check, and the "Continue with" buttons are drawn only after it has.

## Connecting to your own server

The *My own server* screen (`server` in `mobile/src/ui.js`) asks for one thing, the address, and says what the address has to be:

- The field's hint: "The address you open Little Archive at in a browser, for example https://archive.example.com. It must start with https://."
- Under the form, "before you connect": the phone has to be able to reach the server (a public https address from anywhere, a home-network address only on the same Wi-Fi), and plain http is refused on a home network too.
- A link, "Self-hosting guide (opens in your browser)", to [`docs/self-hosting.md`](self-hosting.md) in the project's public repository (`SELF_HOSTING_GUIDE` in `ui.js`). The project has no separate documentation site; the address is the repository's, from the README, with the guide's path on `main`. The link has `target="_blank"`, which leaves the web view for the phone's browser, the same way "Open original" does in the interface.

Focus arrives on the heading, not the field, so the keyboard does not cover the guidance.

What a typed address can run into, and what the screen says on the address field (`ownServerProblem` and `checkServer` in `mobile/src/setup.js`; `discover` keeps its shorter sentences for the hosted service, where Wi-Fi and certificates would be out of place):

| What happened | What it says |
| --- | --- |
| The address is `http://` and not this device | It is not encrypted, use an https address, and the guide covers this under "Reverse proxy". Nothing is sent. |
| Nothing answered (no route, server stopped, a certificate the phone refuses) | Could not reach it: check the address, that the server is running, and the network (a home server answers only on its own Wi-Fi); a certificate the phone does not trust is refused. The native client reports all of these the same way, so the sentence names each. |
| `localhost` or `127.0.0.1` did not answer | On a phone, that address is the phone itself. |
| Something answered that is not Little Archive (a 404, another site's page, other JSON) | It answered, but not as a Little Archive server: use the address you open in a browser, with its port; if that is the address, the server needs an update. |
| A redirect | The app does not follow redirects; enter the address it ends at. |
| A hosted-mode server that names another sign-in service | It runs in hosted mode and uses a sign-in service this app does not trust; a server of your own has to run in self-hosted mode. |
| A hosted-mode server that names the pinned sign-in service | It works: the account screen opens with a notice that this is a hosted service, so there is no owner password. |

Checked by `mobile/tests/discovery.test.mjs`, `onboarding.test.mjs` and, in a DOM, `server-screen.test.mjs`. Not looked at on a simulator or a phone: how the guidance sits on a small screen, and the link opening the browser.

## Continue with Google and Apple

On the hosted account screen the two buttons sit above the email form, which is unchanged. Everything goes through Supabase Auth's REST routes, as the email sign-in does: no Supabase or Google or Apple SDK, no Google client id, no Apple key or secret, and no new key in `app.config.json` (`config.js` still allows exactly its three). A self-hosted server's screens have none of this.

| | iOS | Android |
| --- | --- | --- |
| Continue with Apple | the system sheet (`ASAuthorizationController`), identity token to Supabase | not offered (the button is not drawn) |
| Continue with Google | `ASWebAuthenticationSession`, then a code exchange with PKCE | a Custom Tab, then the same exchange |

**The server needed no change.** `server/identity.py` verifies the access token's signature, issuer, audience, expiry, subject, `role` and `is_anonymous` and returns the account id, issue time and expiry (`Identity(user_id, issued_at, expires_at)`); nothing there, or in what uses it, reads the provider, `app_metadata`, `amr` or the email. A Google or an Apple session is an account like any other. ([hosted mode](hosted-mode.md#what-is-not-verified) says so too.)

### Apple (iOS)

`SocialSignInPlugin.swift` shows Apple's sheet with the email and full-name scopes (`ASAuthorizationAppleIDProvider`) and returns the identity token. The page (`mobile/src/social.js`) makes a random raw nonce, gives the plugin its SHA-256 as **lower case hex** (the plugin sets it as the request's `nonce`, so Apple signs it into the token), and sends `POST <supabaseUrl>/auth/v1/token?grant_type=id_token` with `{"provider": "apple", "id_token": …, "nonce": <the raw nonce>}`. The project hashes the raw value the same way and compares it with the token's `nonce` claim, so the raw nonce never reaches Apple or the native side and a token alone is no use. The full name is requested because Apple's sheet offers it with the email, and is neither read nor kept by the app (Apple gives it only the first time, and Supabase's `signInWithIdToken` has no field for it).

Entitlement: `com.apple.developer.applesignin` = `Default` in `App.entitlements`. A simulator build still succeeds with it (see [what was verified](#what-was-and-was-not-verified)); on a device it needs the capability on the App ID ([checklist](#what-to-switch-on-and-create-the-owner-checklist)).

### Google (iOS and Android)

1. The page makes a random code verifier (64 characters of base64url) and keeps it in memory, and asks the project once whether Google is switched on: `GET <supabaseUrl>/auth/v1/settings` with the publishable key, which answers `{"external": {"google": true, …}}`. The sign-in stops here only when the answer says Google is off (`external.google` is `false`, or an error whose code says the provider is disabled) or when the service cannot be reached. Any other answer (a rate limit, an error page, a shape the app does not know) opens the browser.
2. It opens `<supabaseUrl>/auth/v1/authorize?provider=google&redirect_to=littlearchive://auth-callback&prompt=select_account&code_challenge=<base64url SHA-256 of the verifier>&code_challenge_method=s256` in the system authentication session (iOS) or a Custom Tab (Android). Supabase sends the person to Google and, when they are done, back to `littlearchive://auth-callback?code=…`. `prompt=select_account` makes Google show its account chooser every time, so signing in again after signing out does not silently reuse the Google account the browser remembers; Supabase passes query parameters it does not own on to the provider.
3. The page trades `POST <supabaseUrl>/auth/v1/token?grant_type=pkce` with `{"auth_code": <the code>, "code_verifier": <the verifier>}` for a session. A code lasts five minutes and is good once, and is useless without the verifier of the attempt that made it.

**Shapes checked against Supabase.** Supabase's PKCE guide page does not document the REST requests (it describes the SDK), so the shapes above were read from the source that implements them (auth-js `GoTrueClient` and `helpers`, and the Auth server's `api.go`, `settings.go`, `external.go`, `token.go`, `pkce.go`, `token_oidc.go`, as they stood in November 2026; the settings route and the forwarding of `prompt` were read at commit `3e79d85`) and from the error-codes page. They are: `grant_type=pkce` with `auth_code` and `code_verifier`; `grant_type=id_token` with `provider`, `id_token`, `nonce`; the challenge method is spelled `s256` (the server also accepts other cases and `plain`). Details that matter:

- The nonce Apple signs must be the **hex** SHA-256, because the server compares `fmt.Sprintf("%x", sha256(raw))`; base64 would fail.
- **For a provider that is switched off, `/authorize` answers a 400 page** (`validation_failed`, "Unsupported provider: provider is not enabled") and does not redirect back, so the system browser would show it as raw text and the app would only ever hear "cancelled". That is why step 1 exists: it turns that answer into a sentence before any browser opens.
- **Step 1 reads the settings, not the authorize address.** `GET /settings` is registered beside `/authorize` with no sign-in required (`api.go`), returns each provider's `Enabled` flag (`settings.go`), and writes nothing. An earlier version of this change asked the authorize address itself, which makes the server store a flow-state row per question (cleaned up after 24 hours) and which stopped the sign-in on any answer but a redirect. Two things are read from the source and **not run against a real project**: that the hosted gateway in front of the Auth server accepts the publishable key on this route as it does on the others, and the answer's shape. If either is not so, the answer is not one that says "off", so the browser opens anyway.
- **What the settings cannot see.** They report only whether Google is enabled. A project with Google enabled but no client secret saved still gets the 400 page from `/authorize` ("missing OAuth secret"), in the browser, and the app hears "cancelled". The authorize question caught that case; the settings question does not. Enter the client id and the secret together ([the checklist](#what-to-switch-on-and-create-the-owner-checklist)).
- `prompt` is not among the parameters the server keeps for itself (`reservedOAuthParams`: client id and secret, redirect URI, response type, state, the PKCE values, nonce), so `external.go` adds it to the address it sends the browser to at Google.

### The callback address, and what else uses the scheme

The scheme `littlearchive` was already registered in `Info.plist`, for the share extension: it asks iOS to open `littlearchive://share`, which reaches the app as `appUrlOpen`, which only wakes the share inbox. The sign-in callback is `littlearchive://auth-callback`, a different host, and does not touch that path:

- **iOS.** `ASWebAuthenticationSession` is given the scheme and hands the callback to its own completion handler; the callback of a Google sign-in is never delivered to the app as an opened URL, so the share inbox does not see it, and a `littlearchive://auth-callback…` opened by another app is never the answer to a sign-in. An address opened from outside (a reset link's redirect, or another app) reaches the page as `appUrlOpen` and is read only as a password-reset link ([A forgotten password](#a-forgotten-password)).
- **Android.** `AndroidManifest.xml` has one new intent filter, `VIEW` with scheme `littlearchive` and host `auth-callback` only (Android had no share-wake filter for `littlearchive://share`; its share is the `SEND` filter, unchanged). The filter is exported and browsable, as it must be for the browser to reach it, so **any app on the phone can send that address too**, and `SocialSignInPlugin` cannot tell such an intent from the browser's own redirect. What happens to it:
  - *While a sign-in is waiting*, whichever arrives first is taken as the answer and the attempt ends with it. It cannot sign anyone in: the page trades the code together with its own verifier, and the project refuses a code that was not made for that attempt's challenge. So another app can make one attempt fail ("That sign-in did not finish. Try again.", or "Google did not finish signing you in." for an address that carries an error), and the person tries again. It cannot read the real code, which goes to this app only.
  - *With no sign-in waiting* and the app running, the plugin sends it to the page as a `callback` event. The page takes it only when this phone is waiting on a password-reset link, or when the address carries the project's "link expired" code; otherwise it is dropped, as before.
  - *When it starts the app in a new process*, the app says **"Sign-in was interrupted. Try again."** on its first screen, once, unless this phone is waiting on a password-reset link, in which case the address is that link (`launchCallback` in `recovery.js` finds the address, `openLink` in `onboarding.js` decides; the code of an interrupted sign-in is never used). It knows from the plugin, which keeps a callback that arrived before the page first asked (`interrupted()`, which now hands over the address as well; Capacitor hands the plugin the intent the activity was created with as well as later ones, so both ways Android can deliver the callback to a fresh process are covered), and, for a native side without that method, from the address the app was launched with. This is mainly for the real case: Android ended the app's process while the browser was in front, so the redirect arrives in a fresh process whose verifier is gone. Another app starting this one with the same address gets the same sentence, which is harmless.

### Rules the code holds

- **Pinned, by the order the app works in.** See above. The account screen, both buttons and every request to the sign-in service are made in two places in `mobile/src/onboarding.js`: `hostedSignIn` (every sign-in, and the request for a reset link) and `openLink` (a reset link that opened the app: the code exchange, the new password, the sign-out on Cancel). Each is reached only after `discover` has confirmed that the server names the pinned service, and each checks that again itself. `mobile/tests/onboarding.test.mjs` runs those same functions: before the server has answered, and after an answer that names another service, there is no account screen, no sheet and no request to any sign-in service. Nothing in the flow accepts an address from the server, the page or the callback: the browser is sent to an address built from `supabaseUrl`, and the callback must be exactly `littlearchive://auth-callback` (case aside, optionally a trailing `/`, a query and a fragment; a different host, a path, a userinfo part or another scheme is refused).
- **Callback safety.** A callback is read as the answer to a sign-in only when this app started that sign-in and it is still waiting: the sign-in code has no listener of its own for opened URLs (the one listener is for password-reset links, and it never feeds a sign-in), one attempt can be open at a time (a second tap is refused, and the account screen is locked while any sign-in is on its way), and a PKCE code that is not the one for this attempt cannot be traded. On iOS only the authentication session can deliver that answer; on Android another app can deliver one too, which fails the attempt and nothing more ([above](#the-callback-address-and-what-else-uses-the-scheme)). A callback with an `error`, `error_code` or `error_description` (read from the query and from the fragment, where Supabase repeats them) or without a `code` is refused with a sentence made from the error *code*; the text the address carried is never shown. Closing the sheet, or the Custom Tab, is not an error: the screen simply becomes usable again (Android has no close signal, so a resume with nothing returned means the tab was closed).
- **Memory only.** (For these two sign-ins. A password reset has to keep its verifier across a trip to the mail app, and keeps it in secure storage: [A forgotten password](#a-forgotten-password).) The verifier and the raw nonce live in one function's scope for one attempt, are never written to storage or a log, and are gone when it ends, however it ends (`social.test.mjs` runs success, cancel and error with storage and `console` wrapped). The native side never receives either; it gets the hash and the authorize address.
- **No secrets.** No client secret, `.p8` or service key anywhere. The Google client id and secret are entered in Supabase only; the Apple provider needs no secret for the native flow.
- **Provider switched off.** Until you switch a provider on, the app says so in words: Google, from the settings check (`external.google` is `false`; an error answer that carries `provider_disabled`, `oauth_provider_not_supported` or "Unsupported provider" counts too), before any browser opens: "Google sign-in is not switched on yet. Use your email and password for now."; Apple, from the id_token grant (`provider_disabled`, 400): the same sentence for Apple. An Apple token for a bundle id the Apple settings do not list is refused by the server with "Unacceptable audience in id_token" (an OAuth `invalid request`, no `error_code`); the app says "Apple sign-in is not set up for this app yet."
- **No email.** Apple may withhold the email. `sessionFrom` reads it as the empty string, nothing downstream needs it (`credentials.email` is `''`, the secure-storage record does not check it, the Settings sentence in `ui/src/features/dialogs/settings.tsx` already leaves the email out when it is empty and says "Signed in to a Little Archive account."), and a test runs a session with no email through all of that. A private relay address (`…@privaterelay.appleid.com`) is just an address.
- **Same session machinery.** A session from either provider is the same `{type: 'supabase', …}` record, stored, refreshed (`grant_type=refresh_token`) and ended (`/logout?scope=local`) like an email one, and Delete my account works the same.

### Design

The two buttons are drawn in the page, modelled on each brand's button guidelines, and are **not** the brands' own components or artwork. Each is 48px high (finger sized), a pill like the app's other buttons, with its logo as a decorative SVG and its words as its accessible name.

- **"Continue with Apple"** is black with a white logo (white with a black logo in the dark theme), in the system font. Two things differ from Apple's Sign in with Apple button guidelines: the logo is an Apple mark drawn as an inline SVG path, **not the logo artwork Apple supplies** for this button, and the title is 16px in a 48px button (a third of its height), **smaller than the proportion Apple suggests** (about 43% of the button's height, which would be about 21px). Neither is fixed yet. Offering Sign in with Apple beside Google is what App Store guideline 4.8 asks of an app with a third-party sign-in; whether App Review accepts this drawing of the button is not known, and it is a small review risk ([risk 11](#open-risks-and-decisions-you-may-want-to-reverse)).
- **"Continue with Google"** uses the colours of Google's light button (white, 1px `#747775` stroke, `#1F1F1F` text) and dark button (`#131314`, `#8E918F`, `#E3E3E3`) with the four-colour G. The font is Roboto only where the phone has it, and the system font otherwise (so on iOS), where Google's guidelines name Roboto.

**Behaviour.** The buttons are outside the email `<form>`, so Return in the password field still submits the email form and the keyboard's accessory bar still walks the email and password fields.

- **One lock for the screen.** While any sign-in is on its way (a sheet or the browser is open, a code is being traded, or the email form was sent) the two tabs, both "Continue with" buttons, the form's button, Show password and Back are disabled, and Return does not send the form. Two sign-ins therefore cannot overlap and leave a session that nothing holds. The text fields are not disabled (that would drop focus and the keyboard). When the screen has its answer the lock stays until the app draws the next screen.
- **What the pressed button says.** "Opening Apple…" or "Opening Google…" while the sheet or the browser is up, then "Signing in…" once it has closed and the app is asking Supabase for the session. The button is `aria-busy`, and each change is also said through the screen's live region.
- **A failure** shows under the buttons and is tied to the button that was pressed (`aria-describedby`), which takes focus again, so a screen reader reads the button and then the reason. Closing a sheet says nothing.
- **Focus** never falls to the page body (`ui/DESIGN.md`). On arrival and after switching between Sign in and Create account it is on the heading; when the screen has a notice (after "We sent a message…", or "Your sign-in ended") it is on the notice; after a closed or failed sheet it is back on the pressed button. A button that was pressed by touch is focused without a focus ring (the ring is for the keyboard); one pressed from a keyboard keeps it.
- With the buttons showing, the screen does not put the keyboard up by itself (it would cover them); the email field takes focus on arrival only when there are no buttons.

`mobile/tests/account-screen.test.mjs` checks the lock, the focus moves, the error and the announcements in a DOM (jsdom, taken from the interface's install in `ui/node_modules`; the test skips where that is not installed, as in a job that installs only `mobile/`). It cannot check what is drawn: the missing focus ring was looked at in the simulator, not tested.

Apple's "Hide My Email" gives a different, relay address, which makes a separate account and library (see the risks).

## A forgotten password

For a hosted account that signs in with email and password. It is Supabase Auth's own flow, by its REST routes, with no SDK and no new setting in `app.config.json`. The code is `mobile/src/recovery.js`, the screens are `forgot` and `newPassword` in `ui.js`, and the order is in `onboarding.js`.

1. **Sign in view, "Forgot your password?"** (a button under the form, under the screen's one lock). It opens *Reset your password*, with the email typed so far carried over.
2. **The request.** The app makes a PKCE pair exactly as "Continue with Google" does (`pkcePair` in `social.js`), keeps the verifier, and sends `POST <supabaseUrl>/auth/v1/recover?redirect_to=littlearchive://auth-callback` with `{"email", "code_challenge", "code_challenge_method": "s256"}` and the publishable key. `redirect_to` is the address already on the project's allow-list for Google.
3. **The same sentence for every address.** Back on the sign-in screen: "If that address has an account, a reset link is on its way. Open the link on this phone, soon: it stops working after a few minutes." The app says this whatever the service answered, and says something else only when the service could not be reached. The answers do differ: an unknown address is a 200 with nothing sent, a known one asked twice within a minute is a 429 (`over_email_send_rate_limit`), so showing either would tell a stranger which addresses have accounts.
4. **The link.** The email's link opens the project's page in the phone's browser (`GET /auth/v1/verify?token=pkce_…&type=recovery&redirect_to=…`), which redirects to `littlearchive://auth-callback?code=…`, which opens the app.
5. **Choose a new password.** The app asks the server the link was asked for what it is (the same discovery and pin as any sign-in), trades the code and the kept verifier (`POST /auth/v1/token?grant_type=pkce`), and shows *Choose a new password*: the new password twice, the sign-up form's rule (at least 8 characters) and a show-password toggle on each field. It sets it with `PUT /auth/v1/user` (`{"password"}`, the link's session as the bearer token) and carries on signed in. The session is kept in secure storage only after the password is set; Cancel ends it (`/logout?scope=local`).

**Email sign-up has no PKCE, and this does.** `signUp` sends only the email and password, and its confirmation link is not handled by the app (risk 8). A reset without a challenge would come back as `littlearchive://auth-callback#access_token=…&refresh_token=…&type=recovery`: a session in an address. Any app can open that address, so the app would be signing in to whatever account someone else put there, and a session in an address can be read on its way. So the app sends a challenge, and `parseCallback` reads a code or an error from a callback and nothing else; an address with tokens in it is refused ("That link did not come back the way it should. Ask for a new one."). The pieces are the Google sign-in's: `pkcePair`, `parseCallback`, `CALLBACK_URL`, `exchangeCode`.

**What PKCE costs here.**

- *The verifier is written down.* The person leaves for their mail app and the phone may end the app meanwhile, so the verifier cannot live in memory as a Google sign-in's does. It is one record in secure storage (`recovery`: the verifier, the server, the time), removed when the link is used, when a newer link is asked for, when someone signs in, or after an hour. One failed exchange does not remove it: on Android any app can send the callback address with a made-up code, and that must not spoil the real link.
- *The link works only on the phone that asked.* Opened on a computer, the browser cannot open `littlearchive://`. Opened on another phone with the app, the app says "That reset link was not asked for on this phone, or a newer one has been asked for since. Ask for a new one here, then open it on this phone."
- *A few minutes.* Read from the Auth server's source, not run against a real project: the code exchange is refused once the *request* is older than the flow-state lifetime, five minutes by default (`internal/models/flow_state.go`, `IsExpired` measures from the flow state's creation except for a magic link; `External.FlowStateExpiryDuration`, default and floor 300 seconds in `internal/conf/configuration.go`; `recover.go` creates the flow state when the link is asked for). The emailed link itself lives for the project's "email OTP expiration". So a link opened after five minutes comes back with a code the project will not trade, and the app says "That reset link has run out or was already used. Ask for a new one, and open it within a few minutes." That is why the sentence in step 3 says "soon". If mail is slow to arrive this will be a nuisance; see [risk 16](#open-risks-and-decisions-you-may-want-to-reverse).

**Shapes read from source** (the Auth server's `recover.go`, `verify.go`, `user.go`, `mail.go`, `pkce.go`, `token.go`, `models/flow_state.go`, `conf/configuration.go`, and auth-js `GoTrueClient.ts` and `lib/fetch.ts`, on their main branches in November 2026; none of it run against a real project):

- `recover` takes `email`, `code_challenge`, `code_challenge_method` in the body, and auth-js puts `redirect_to` in the query. An address with no account is answered `200 {}`, the same as success. The per-address limit (one mail a minute by default) is a 429 and is checked only once the account is found.
- The token of a PKCE link starts with `pkce_`; `verify` then redirects with `?code=`. Without the prefix it redirects with the session in the fragment.
- A link that is too old or already used redirects with `error_code=otp_expired` and "Email link is invalid or has expired", in the fragment and, for a PKCE link, in the query too. The app reads the code and never shows the text.
- `PUT /user` takes `password`, answers 200 with the user, refuses the current password with `same_password` (422), and a weak one through its strength check. The server's own minimum is 6 characters by default; the app asks for 8, as its sign-up form does.
- Not read: what the server does to other sessions when a password changes, and whether the hosted project's "secure password change" or "require current password" settings refuse a recovery session. If either refuses, the person sees the service's own short message on the form.

**An account that only uses Google or Apple** gets the same sentence. By the source the project looks the account up by email alone, so it would be sent a link too, and setting a password would give that account a password as well; the stand-in does the same. The reset screen says "Signed up with Google or Apple? There is no password to reset: go back and use that button."

**How the link reaches the page** when no sign-in is waiting for a callback:

| | App running | App not running |
| --- | --- | --- |
| iOS | `appUrlOpen` from `@capacitor/app` | `App.getLaunchUrl()`, and the `appUrlOpen` event Capacitor keeps for the first listener |
| Android | a `callback` event from `SocialSignInPlugin`, sent only when no sign-in is waiting | `SocialSignInPlugin.interrupted()`, which hands over the address it set aside (and `App.getLaunchUrl()` for an older native side) |

`createLinkInbox` (`recovery.js`) holds one address until a first-launch screen is about to be drawn or is up (`show` in `onboarding.js`); the flow that was running steps aside, the link is handled, and the flow starts again if the link did not end in a sign-in. With someone signed in, the inbox is closed and a link is ignored. On Android the same address is also what a Google sign-in looks like when the system ended the app while the browser was open, so there the app treats it as a reset only when this phone is waiting on one or the address says `otp_expired`; otherwise it is the old "Sign-in was interrupted. Try again." (cold start) or nothing (app running). With a reset waiting, an interrupted Google sign-in would be answered with the "ran out" sentence instead; that needs both to happen within the hour.

**The order holds.** Nothing goes to the sign-in service before the server has answered and named the pinned service: the request is made from the account screen, and a link that opens the app cold has the server it was asked for (kept with the verifier) asked first. `onboarding.test.mjs` checks both, including a server that cannot be reached or names another service: no request, no new-password screen, and the verifier still there.

**Accessibility.** Each field has a real label; the email is `autocomplete="username"` and both password fields `new-password`, with a hidden username field on the new-password form so a password manager files the new password under the right account. Focus goes to the heading of each new screen (the problem screens too, whose message is an `alert`), to the notice when the sign-in screen comes back with the sentence, and to the field that is wrong after an error, where the reason is tied to it (`aria-invalid`, `aria-describedby`). A failure that belongs to no field is an `alert` above the form. Every button is at least 44px (`.btn.small`; the show-password toggle was 40px and is now 44). Nothing here scrolls or moves the page by script: the screens are ordinary documents in a web view that ends at the keyboard, and the one helper that existed (`showField` in `ui.js`) is unchanged. `reset-screens.test.mjs` checks the state in a DOM; none of it was heard with VoiceOver or TalkBack.

**The owner's side.** The redirect allow-list entry `littlearchive://auth-callback` (step 2 of [the checklist](#what-to-switch-on-and-create-the-owner-checklist)) is what a reset needs, and Google already needed it. The project's "Reset password" email template has to carry the project's own confirmation link (`{{ .ConfirmationURL }}`, the default); a template that links somewhere else, or that only shows a code, would not open the app. Whether the hosted project's default template does this for a PKCE request was not checked against the real project. Mail scanners that open links in incoming mail use the link up before the person does, and it then says "ran out"; that is a known limit of one-time links.

**Trying it against the stand-in.** `mobile/dev/stub_supabase.py` answers `recover`, `verify` and `PUT /user` by the rules above, sends no mail, and lists what it would have sent at `http://127.0.0.1:<port>/stand-in-mail`: open that page in the simulator's browser and tap the link. `STUB_OTP_TTL`, `STUB_MAIL_GAP` and `STUB_CODE_TTL` set the three lifetimes.

**Verified and not.** Run: the Node tests (`recovery.test.mjs`, `supabase.test.mjs`, `onboarding.test.mjs`, the screens in jsdom in `reset-screens.test.mjs`, and the app's code against the stand-in over loopback in `stub-roundtrip.test.mjs`) and the stand-in's own rules (`tests/test_mobile_stub_supabase.py`). **Not run: anything on a simulator, an emulator or a phone.** The app was not built with this change; the Android plugin's change (`SocialSignInPlugin.java`: the address kept for `interrupted()`, the `callback` event) was **not compiled**. Not seen: a link opening the app on either platform, `appUrlOpen` and `getLaunchUrl` carrying the address on iOS with the scene delegate, the screens themselves in either theme, the keyboard on the new-password form. Not contacted: the real Supabase project, so the request's shape, the email, the link and the five-minute limit are from source only.

## Security model

- **Where credentials live.** One record in the platform's secure storage through [`@aparajita/capacitor-secure-storage`](https://github.com/aparajita/capacitor-secure-storage) 8.0.1: the iOS Keychain (accessible only while the phone is unlocked, this device only, never iCloud Keychain) or Android Keystore AES-GCM keys with the data in app-private storage. The record holds the server, and the device token or the Supabase tokens. The owner password is never stored; neither is a Supabase password.
- **No fallback to `localStorage`.** That plugin falls back to `localStorage` in a browser. The shell refuses to start unless Capacitor reports a native platform, so a credential is never written there.
- **Fresh install means signed out.** iOS keeps Keychain items after the app is deleted. The shell keeps a flag in the web view's storage (deleted with the app) and clears the Keychain record when it is missing.
- **Android backup is off** (`allowBackup=false`), so a backup cannot copy the token off the phone.
- **Server addresses.** `https` always. Plain `http` only for this device (`localhost`, `127.x`, `[::1]`, `*.localhost`), and, in a bundle built with `LA_DEBUG_BUILD=1` only, the Android emulator's `10.0.2.2` (a build-time constant, not something a page, a setting or a stored value can switch on); a server on a home network without a certificate is refused with an explanation. iOS carries `NSAllowsLocalNetworking`; Android release builds forbid cleartext to every host, debug builds allow it for `localhost`, `127.0.0.1` and `10.0.2.2` only (`src/debug/res/xml/network_security_config.xml`). `mobile/tests/android-network.test.mjs` checks that the two Android configs and the address check agree, and `tests/build.test.mjs` that a release bundle holds no trace of the emulator host. A loopback `http` address still passes the app's own check in a release build while Android's release config blocks it, so it fails at the platform rather than being offered; that is the fail-closed side of the difference.
- **Redirects are never followed** (the native client is told not to), so the token cannot be sent to a second address. A redirect is shown as an error.
- **Cookies.** The app never calls a cookie-issuing route, and the transport drops `Set-Cookie` from what it hands to the interface. Capacitor's native client does keep cookies a response sets in the platform's cookie store (nothing the app calls sets one). The server's rules are untouched: in hosted mode a cookie is never a credential, and in self-hosted mode a presented bearer token is judged alone.
- **The web view reaches nothing itself.** The app's content security policy is the server's, plus `blob:` for thumbnails, with `connect-src 'self'`, `frame-src 'none'` and no inline or eval script.
- **Shared text is untrusted.** It passes through the same `parseSharedContent` as a browser share (http and https links only, no credentials in the link, hidden and direction characters removed, length limits), only fills form fields, and never saves by itself. The native side caps its length and passes strings only. The Android plugin accepts `text/*` intents only; the iOS extension reads a URL or plain text attachment only.
- **Exports are temporary.** An export or backup is written to the app cache so the share sheet can take it, and removed the next time the app starts and before the next export.
- **Signing out** revokes the device token on the server (`POST /api/auth/logout`) or ends the Supabase session, then clears the phone whether or not the server could be reached.
- **A password reset keeps one secret for up to an hour.** The PKCE verifier of a reset that was asked for is in the same secure storage as the sign-in, under its own name, with the server it was asked for and the time. It is removed when the link is used, when a newer link is asked for, when someone signs in, or when it is an hour old. It is of use only together with the code in the emailed link. A session is never read from an address that opens the app ([A forgotten password](#a-forgotten-password)).
- **Continue with Google and Apple** adds no stored secret: the PKCE verifier and the Apple nonce are in memory for one attempt, and the browser session or sheet is the system's, not a web view of the app's ([the section](#continue-with-google-and-apple)).

## The one-time purchase

One product, bought once, opens recipe cards, places, ask your archive and the larger allowances of a hosted account. It is a **non-consumable on the App Store and a one-time product on Google Play, both with the product id `unlock_full`**. No subscriptions, no ads, no third-party purchase service, no credit packs. The server is the only thing that unlocks an account: it checks the store's proof with the store ([hosted mode](hosted-mode.md#purchases); the answers are in `API_CONTRACT.md`). The app only carries the proof.

**A self-hosted server has no purchase at all.** Its bridge has no `purchases` (`mobile/src/bridge.js` refuses to build one), the unlock screen says everything is open and there is nothing to buy (`unlockView` in `ui/src/features/unlock/purchase.ts`), and nothing in the app asks the store anything. The iOS plugin is registered at launch like every plugin and, as StoreKit asks of every app, listens to `Transaction.updates` from the start; with no purchases on the page there is nobody to tell.

### The plugin: custom, in the app, one per platform

`StorePurchasesPlugin.swift` (190 lines, StoreKit 2) and `StorePurchasesPlugin.java` (312 lines, Play Billing Library 9.1.0) sit beside the share plugin, as app code, not packages. `mobile/src/purchases.js` (199 lines, with its tests) is the only code that decides anything. **No new package is added to `package.json`.**

Why not a maintained plugin: the candidate that supports Capacitor 8 and Swift Package Manager, `@capgo/native-purchases` 8.9.16, was downloaded and read. It does return the StoreKit 2 `jwsRepresentation` and the Play `purchaseToken`, declares `capacitor-swift-pm` `from: "8.0.0"` in a `Package.swift`, and would have worked. It was not chosen because it is a subscription-oriented plugin of several thousand lines (offers, introductory eligibility, subscription management, a manifest that looks for installed SDK files while it resolves) of which the unlock needs a small part; because its defaults finish the Apple transaction and acknowledge the Google purchase on their own before the server has seen the proof (both can be switched off, but the order is the whole point); and because it brings its own `Transaction.updates` listener, a second thing to keep out of the way. A purchase path of a few hundred lines on Apple's and Google's own libraries is the smaller thing to read, test and trust. RevenueCat and similar services were excluded by the brief.

What was verified for the choice: the StoreKit symbols used (`VerificationResult<Transaction>.jwsRepresentation`, `Transaction.unfinished`, `.currentEntitlements`, `.updates`, `finish()`, `Product.purchase(options:)` with `.appAccountToken`, `purchase(confirmIn:)`, `AppStore.sync()`) are in the iOS 26.5 SDK's StoreKit interface, and the plugin compiles for the simulator; the Billing Library 9.1.0 calls used (`enablePendingPurchases(PendingPurchasesParams)`, `enableAutoServiceReconnection`, `queryProductDetailsAsync` with `QueryProductDetailsResult`, `queryPurchasesAsync(QueryPurchasesParams)`, `setObfuscatedAccountId`, `acknowledgePurchase`, `AccountIdentifiers`) were listed with `javap` from the library's AAR, and the plugin compiles in `./gradlew assembleDebug`. The deployment target is iOS 15 and the minimum SDK Android 24.

### What happens

1. **The price.** `product()` loads `unlock_full` and returns the store's own localized price. On the App Store a product that is not a non-consumable is never sold. With no price the screen shows none.
2. **Buying.** The unlock screen asks the server who this account is (`GET /api/account`), then `buy({ accountId })`. The purchase is bound to the account: Apple's `appAccountToken` is the account's UUID, Google's obfuscated account id is the lowercase hex SHA-256 of it (`accountTag` in `purchases.js`).
3. **The proof goes to the server, from the interface.** The StoreKit JWS to `POST /api/purchases/apple`, or `{product_id, purchase_token}` to `POST /api/purchases/google`.
4. **Only then is the store told.** On `200` the Apple transaction is finished. For Google the server acknowledges the purchase itself when it can and says so (`acknowledged`); the app acknowledges only when that is `false`, never both. A `400` or `409` `purchase_*` refusal is final: the Apple transaction is finished so it is not offered at every start; a Google purchase is left unacknowledged (Google refunds it after three days). Anything else, such as a network failure, `503`, `429`, leaves the purchase open.

| Case | What the person sees, and what stays |
| --- | --- |
| closed the sheet | "No purchase was made." Nothing is sent. |
| Ask to Buy, or a Play payment still pending | "Your purchase is waiting for the store." Nothing is sent. When it completes, `Transaction.updates` (Apple) or the purchases-updated callback (Google) wakes the app, which sends it; if the app was closed, the next start does. The interface refreshes itself and says so. |
| Google answers `202` (the payment is not complete) | "The store is still completing the payment", with Check again. The next start sends it again. |
| already owned | Apple returns the existing transaction; Google answers `ITEM_ALREADY_OWNED` and the plugin hands over the purchase it holds. Both go to the server as a restore (`restored: true`). |
| the phone was offline, or the server unreachable, after paying | The transaction stays unfinished (Google: unacknowledged). It is sent again at the next start, when the app comes back to the front, and on any update from the store. |
| Restore | Apple: `AppStore.sync()` (which may ask for the Apple ID), then every current entitlement. Google: what Play holds. Each is sent; the first the server accepts wins. |
| the server refuses | The server's reason, in words: another account holds it, the store took it back, it is not this app's unlock, the wrong environment. |

**A purchase is never given to a different account by the app.** The background pass (start, resume, store updates) sends only a purchase bound to the signed-in account, or bound to none, because the server gives a purchase to the first account that presents it. Restore, pressed by the person, sends everything the store account holds.

## Share from other apps

**Android.** `MainActivity` has an `ACTION_SEND`, `text/plain` intent filter. `ShareInboxPlugin` (in `android/app/src/main/java/app/littlearchive/mobile`) keeps the latest share (from `onCreate` or `onNewIntent`) until the web side takes it, then clears the intent so a recreated activity cannot deliver it twice.

**iOS.** `ShareExtension` (its own target) receives a URL or text, stores `{title, text, url}` as JSON in the App Group `group.app.littlearchive.mobile`, and asks iOS to open `littlearchive://share`. The app's `ShareInboxPlugin` reads and clears it. The App Group carries the data, so a share is not lost if iOS declines to open the app from an extension; it is waiting the next time the app opens. Opening the app from an extension uses the responder chain, which is unofficial and best effort (see risks).

In both, the shell takes a pending share only when the interface can show it (on start, on resume, and on `appUrlOpen`), then the interface opens the ordinary save dialog.

## Open risks and decisions you may want to reverse

1. **Account deletion deletes the Supabase Auth user, on the server, and the dialog now says which of three things happened.** `POST /api/account/delete` removes the library and unlock records and then the sign-in with the operator's secret key ([hosted mode](hosted-mode.md#account-deletion)). The key lives only on the server; a publishable key and a user's own token cannot delete an Auth user. The answer says which happened and the interface (`ui/src/features/dialogs/words.ts`, with tests) reads it: `auth_user_deleted: true` ("your library and your sign-in are both gone"), `auth_deletion: "pending"` (the server keeps retrying; the server's own sentence is shown), or `auth_deletion: "not_configured"` (a server run without the key on purpose; the dialog says the email is still registered with its provider and to ask whoever runs the service). The old line that said the email stays registered is gone from the app. Checked only against a stand-in for Supabase. The old buildless interface (`web/app.js`) still has that line in its own copy of the dialog; the app no longer loads it.
2. **Opening the app from the iOS share extension is unofficial.** It uses the responder chain; Apple has changed this behaviour before and may again. The share is stored in the App Group either way, so the failure mode is "open the app yourself", not data loss, and the extension says so. Apple has accepted this pattern in many apps, but it is not documented API.
3. **Plain http is refused except for this device.** A home-network server needs https (the [phone guide](phone.md) already says so). This is the conservative choice for store review and for the owner password; allowing private-network http is a policy change in `server-url.js` and the iOS and Android network configs.
4. **Native HTTP does not follow redirects.** A server behind a proxy that redirects `http` to `https` must be entered with its `https` address; a redirect is reported as an error rather than followed.
5. **The privacy manifest and `ITSAppUsesNonExemptEncryption=false`** are starting points that match what the app does (an email address, what you save and, once a hosted account buys the unlock, the App Store's signed receipt for it go to the server you chose; HTTPS and the Keychain only). The manifest declares email, other user content and purchase history, all linked to the account, for app functionality, none for tracking. StoreKit and the Billing Library need no usage-description string and, on iOS, no entitlement key, so `Info.plist` and the entitlements did not change. They are your declarations to the stores: check them against your own answers before submitting.
6. **Thumbnail memory.** Up to 400 thumbnails are kept as blob URLs and the oldest are released. A very long scroll can release one that is still on screen, which then shows the text cover until it is reloaded.
7. **A token revoked on the server** shows up as a sign-out at the next request (observed), not at the moment of revocation. Hosted access tokens live as long as the Supabase project sets; the server never asks Supabase whether a session was ended ([hosted mode](hosted-mode.md#what-is-not-verified)).
8. **No email-confirmation deep link, no offline mode.** The deep links are the sign-in callback and the password-reset link, which share one address; an email-confirmation link opens a browser at the project's Site URL (set it; see [the checklist](#what-to-switch-on-and-create-the-owner-checklist)).
9. **Deleting an account does not revoke an Apple sign-in.** Apple's technical note TN3194 says an app that offers Sign in with Apple should call Apple's `/auth/revoke` when someone deletes their account; that needs a refresh or access token (obtained by exchanging Apple's authorization code with a client secret signed with a `.p8` key) and the key can only live on the server. This change takes neither: Supabase's `signInWithIdToken` does not carry the authorization code, and no key is in the repository. The fallback Apple's note gives is to delete the data and tell the person to remove the app under Settings, their Apple Account, Sign in with Apple. The delete dialog does not say that yet (`ui/src/features/dialogs/words.ts`); it is a review risk under guideline 5.1.1(v) for an app that offers Apple.
10. **Hide My Email makes a different account.** A person who hides their email gets a private relay address from Apple, which does not match their email account, so Supabase makes a separate account and an empty library for it. There is no way for the app to link them. Mail the operator sends to a relay address reaches the person only if the sending domain is registered with Apple; the app and the server send none, Supabase's own mail (confirmation, reset) is the only mail, and an Apple or Google identity needs neither.
11. **Apple's button is drawn in the page, not by `ASAuthorizationAppleIDButton`, and does not fully match Apple's button guidelines.** It is black or white with an Apple mark, says "Continue with Apple", uses the system font and is finger sized. Two known differences, not yet fixed: the logo is an Apple mark as an inline SVG path, not the logo artwork Apple supplies for this button, and the title is 16px in a 48px button, below the proportion Apple suggests (about 43% of the button's height). A reviewer can object to either, so this is a small App Review risk. The fix is Apple's supplied artwork (download it from Apple's design resources yourself; it is not in the repository) and a larger title, or the native button. The Google button uses the system font on iOS where Google's guidelines name Roboto.
12. **The full-name scope is requested and unused.** It is in the request so that Apple's sheet offers the name with the email, as the first version of this change specified; the app does not read it. Drop `.fullName` in `SocialSignInPlugin.swift` if you would rather not ask.
13. **The keyboard and the status bar: fixed on iOS, proven on the iOS 26.5 simulator only.** The keyboard used to slide the page's top behind the clock, and two CSS attempts failed (a fixed strip; the screen as the scroller inside a fixed parent) because what moved was the web view's visible area, not the document. The web view now ends at the keyboard ([The keyboard](#how-it-is-built)). Left: (a) **iOS 15 to 18 are unverified.** No older runtime was installed. The one difference the sources point to, the web view keeping room for the keyboard after its frame has changed, is removed by not telling the web view about the keyboard, but that was only run on 26.5. (b) Not seen on a physical device or an iPad (floating and split keyboards, Split View, Stage Manager: the layout path that covers them was not exercised). (c) Android was run on WebView 133, where the status bar is an opaque band. From WebView 140, with `viewport-fit=cover`, Capacitor hands the insets to the page and it draws under the status bar; `SystemBars.java` still pads the web view by the keyboard's height on that path (`v.setPadding(0, 0, 0, keyboardVisible ? imeInsets.bottom : 0)`), and its own comment says the WebView ignores `interactive-widget=overlays-content`, so the page should be shortened there as on iOS and the strip should hold. That is read from the source, not run. (d) The selection bar rides above the keyboard by choice (see above).
14. **On Android another app can end a Google sign-in that is waiting.** Any app can send `littlearchive://auth-callback?…` while the browser is open; the attempt then fails with a plain sentence and the person tries again. It cannot sign anyone in or read the real code ([the callback address](#the-callback-address-and-what-else-uses-the-scheme)). Closing that would need the callback to be an https App Link verified for this app, which needs a domain; not done.
15. **The delete-account dialog can name an email that an Apple account does not have.** When the service is not set up to remove sign-ins the dialog says "your email is still registered with its sign-in provider" (`ui/src/features/dialogs/words.ts`, line 10). For an Apple account whose email was withheld there is no email; "your sign-in" would be true for every account. The interface was not changed here.
16. **A reset link has to be opened within about five minutes of asking, on the same phone.** Both follow from sending a PKCE challenge, which is what keeps a session out of the address ([A forgotten password](#a-forgotten-password)); the five minutes is read from the Auth server's source and not confirmed on the real project. If it proves too tight (slow mail), the alternative that keeps the same safety is the six-digit code Supabase can put in the same email (`{{ .Token }}` in the template), typed into the app and traded with `POST /auth/v1/verify`: no link, no five minutes, any device. It needs the email template changed, so it is the owner's call; it is not built.
17. **On Android, a reset link and an interrupted Google sign-in arrive the same way.** The app tells them apart by whether this phone is waiting on a reset. With one waiting, a Google sign-in that the system interrupted is answered with "That reset link has run out or was already used…" instead of "Sign-in was interrupted". Any app can also send the address: with a reset waiting it gets the same sentence and the real link still works afterwards; with none waiting nothing happens while the app is running.

## What is not done

Each of these has a place to attach; none is built.

- **A real purchase, end to end.** The app side is built ([the one-time purchase](#the-one-time-purchase)) and so is the server side ([hosted mode](hosted-mode.md#purchases)); they have not met a real store. What remains is yours: the products and testers in the two consoles, the server's store settings, and a first sandbox purchase on each platform ([the steps](#what-store-setup-is-still-yours)). Self-hosters stay free: the self-hosted server's `OwnerEntitlements` is always unlocked, the purchase routes answer `404`, and the app shows no purchase UI for a self-hosted server. No credit packs.
- **On-device page reading or transcription.** The server routes already accept client-supplied page details and transcripts (`POST /api/items/{id}/page`, `…/transcript`, [understanding](understanding.md)). A native plugin that reads a shared page would call them through `native.fetch` after the save.
- **Push notifications** (for finished closer reads). Needs a token registration route on the server; the shell already has a place to register at sign-in (`boot.js`, after `whoAmI`).
- **Store listings, screenshots, signing and release builds.**
- Larger uploads: `@capacitor/file-transfer` instead of base64 over the bridge.
